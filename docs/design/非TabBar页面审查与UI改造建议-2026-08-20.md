# inviteMaster 非 TabBar 页面审查与 UI 改造建议

审查日期：2026-08-20  
范围：原生微信小程序用户端；本轮只读审查现有代码，不改业务源码。  
参考稿：`inviteMaster-non-tab-ui-reference-v1.svg` / `inviteMaster-non-tab-ui-reference-v1.png`

## 一、结论

项目当前在 `app.json` 中注册 7 个页面，其中 3 个为 TabBar 页面，剩余 4 个均需要纳入同一轮二级页面改造：

| 页面 | 路由 | 核心任务 | 优先级 |
| --- | --- | --- | --- |
| 收到邀请 | `pages/receive/receive` | 分享落地、完整请柬、回复、转发、收藏、地图 | P0 |
| 制作邀请函 | `pages/show/create/create` | 内容编辑、样式、素材、权限、保存/发布 | P0 |
| 模板/作品预览 | `pages/show/show` | 从浏览到制作、从作品到回复的转换桥梁 | P1 |
| 我的资料 | `pages/mine/info/info` | 头像、署名、联系信息和基础资料 | P2 |

此外，以下并非独立路由，但必须与二级页面一起处理，否则视觉和交互仍会断层：

- `responseForm`：预览页和收到邀请页共用的回复表单。
- `material` / `audioCut`：创作中心和编辑器共用的素材与音频裁剪。
- `single-edit`：个人资料的单字段编辑层。
- `half-layout`：回复、编辑、权限和素材等底部弹层的共同容器。

## 二、优先优化项

### P0：发布和主链路

1. **分享落地页必须有完整错误状态**

   `receive.ts` 在邀请码为空时只提示 Toast 后返回，`loading` 仍保持 `true`，页面会停留在“正在展开请柬”。需要改成明确的无效链接页，并提供“返回首页”主操作。

2. **分享地址不能长期使用可枚举数字 ID**

   当前分享路径直接携带 `invitation.id`。正式上线前建议由服务端签发不可枚举、可失效的 `shareToken`，并校验发布、结束、取消和访问权限状态。

3. **编辑器必须拆分**

   `create.ts` 已达 905 行，`create.scss` 1154 行，同时处理模板解析、字段同步、样式、农历、定位、音乐、素材、快照、上传、草稿和发布。建议拆成：

   - `templateCodec`：模板解析、样式单位转换、序列化。
   - `invitationDraft`：草稿初始化、字段同步、脏状态、校验。
   - `snapshotUploader`：快照、临时文件、上传、失败恢复。
   - `audioController`：播放、暂停、切换、销毁。
   - 页面只保留流程编排和视图状态。

4. **预览页和编辑器要支持 query 兜底加载**

   两页目前主要依赖 `EventChannel` 接收完整对象。页面恢复、开发者工具直接打开、入口重构或进程重启后，可能没有事件数据。路由应携带稳定的 `templateId` / `invitationId`，事件通道只作为首屏优化，缺失时通过详情接口恢复。

### P1：工程质量与一致性

5. **当前 `verify` 不是全项目门禁**

   `tsconfig.verify.json` 只包含部分文件，未覆盖 `pages/show/show.ts`、`components/responseForm/responseForm.ts`、`store/template.ts` 等关键链路；`package.json` 也没有 lint、单元测试或 CI。建议优先补齐请求、session、模板序列化、农历、回复表单和编辑保存的测试。

6. **清理日志与宽泛类型**

   当前源码扫描到 107 处 `console.*` 和 185 处 `any`。`show.ts` 会打印页面参数、模板和邀请对象，可能包含用户与邀请数据。需要统一开发日志器、生产关闭、字段脱敏，并从接口边界开始收紧类型。

7. **合并重复基础组件和遗留样式**

   - `components/navigation-bar/` 同时存在 `index.*` 与 `navigation-bar.*` 两套实现。
   - 同时存在 `popup` 与 `popup1`。
   - `material.scss` 前半段仍保留一套蓝色 Web 风格音频裁剪样式，后半段再用宋式主题覆盖。
   - `color-picker` 同时保留 `.less` 与 `.scss`。

   建议确认真实引用后删除未使用版本，避免后续修一个入口、另一个入口继续漂移。

8. **明确深色模式策略**

   `app.json` 开启 `darkmode`，但 `theme.json` 的 light / dark 完全相同。应选择其一：当前版本明确只支持宣纸浅色并关闭暗色声明，或补齐真正的深色令牌与真机验证。

9. **收紧 sitemap**

   当前 `sitemap.json` 允许所有页面。个人资料、编辑器、收到邀请等私有或带用户数据的页面不应被搜索索引。

## 三、非 TabBar 页面 UI 处理重点

### 1. 收到邀请（P0）

- 首屏只保留邀请主题、邀请人、核心视觉和时间地点，不要让装饰抢过内容。
- 底部固定操作按“回复邀请 > 转发 > 收藏”排序；主按钮只保留一个朱砂色。
- 明确加载、无效链接、未发布、已结束、已取消、网络失败六种状态。
- 地点区域同时提供“复制地址”和“地图导航”，无经纬度时只保留复制。
- 回复成功后原位更新按钮为“修改回复”，不要整页刷新。

### 2. 制作邀请函（P0）

- 编辑画布、快捷字段、底部工具、保存发布必须形成稳定的四层结构。
- 内容编辑和参与设置分层，不把所有字段铺在同一屏。
- 保存中、保存失败、已同步、待保存四种状态要可见，离开前拦截未保存变更。
- 素材、字体、颜色、音乐使用同一底部弹层规格；避免不同组件各自定义圆角、标题和按钮。
- 模板加载失败或背景丢失时，使用项目已有 fallback 画面，并允许重新选择模板。

### 3. 模板/作品预览（P1）

- 模板预览使用“收藏模板 / 用此模板”；作品预览使用“收藏 / 回复邀请”，两种业务态不要混用同一套文案。
- 图片或模板数据缺失时显示结构化空态，不能只留下空白舞台。
- 音乐按钮、收藏反馈和制作跳转需支持重复点击防抖与失败恢复。
- 预览页只负责浏览和转换，避免继续堆叠编辑能力。

### 4. 我的资料（P2）

- 头像与署名放在独立身份区；联系信息和基础资料分组。
- 手机号默认脱敏展示；进入编辑层后再显示完整值。
- 保存反馈应贴近当前字段，避免每改一项都用全局 Toast 打断。
- 增加隐私说明，解释资料用于邀请署名或应邀联系的具体范围。

### 5. 共用弹层

- 统一顶部拖拽条、标题、副标题、关闭按钮、内容滚动区和底部安全区。
- 回复表单首屏优先展示回复类型、姓名、手机号和人数；住宿、接送等次要项按选择展开。
- 素材库用“图片 / 视频 / 音乐 / 字体”分栏，上传入口固定在第一项；上传、处理中、失败、可重试要有明确状态。
- 弹层关闭前若有未提交内容，需二次确认。

## 四、参考 UI 规范

- 方向：`Luxury / refined`，宋式雅致与克制装饰艺术结合。
- 色彩：宣纸 `#F5F0E6`、浅纸 `#FBF8F1`、松石 `#2F4A46`、深松 `#173A37`、朱砂 `#B53B2E`、赭金 `#C39445`。
- 字体：标题使用思源宋体，正文使用思源黑体；实现保留中文字体 fallback。
- 构图：邀请函竖向视觉为主轴，细线、窗格和扇形几何作辅助；固定操作区避开底部安全区。
- 圆角：仅用于按钮、头像和必要弹层；信息面板以直角、细边和留白为主。
- 图标：统一细线轮廓图标，不使用 Emoji。

新参考板包含四屏：模板预览、收到邀请、我的资料、回复邀请。它不包含 TabBar，用于补齐现有 v5 母版之外的二级页面。
